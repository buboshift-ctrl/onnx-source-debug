# 인수인계 문서 — ONNX 디버깅 정보 보존 과제

이 문서는 "이 과제를 처음 맡는 사람"이 위에서부터 읽으면 지금까지 뭘 했고 뭘 알아냈고
뭐가 남았는지 알 수 있도록 쓴 것입니다. 용어는 처음 나올 때 풀어서 설명합니다.

---

## 1. 우리가 하는 과제가 뭔가

**국가 R&D 과제** "재구성형 인공지능 프로세서 SW 프레임워크 기술개발"의 **4세부**(디버거·
프로파일러·통합개발환경) 소속입니다. 우리 역할은 **ONNX 파이프라인에 디버깅 정보를
보존**하는 것입니다.

### 왜 이게 문제인가

일반적인 프로그래밍 언어(C, 파이썬 등)를 컴파일하면, 컴파일러가 "이 기계어 명령은 원래
소스코드 몇 번째 줄이었다"는 표(**DWARF**라는 디버그 정보 포맷)를 같이 만들어줍니다.
그래서 `gdb` 같은 디버거로 중단점을 걸고, 변수를 들여다보고, 한 줄씩 실행해볼 수 있습니다.

**ONNX는 이런 게 없습니다.** ONNX는 "신경망 연산 그래프"(Conv, ReLU, MaxPool 같은 연산이
어떤 순서로 연결되는지)만 표현하는 포맷이라, "이 Conv 연산이 원래 PyTorch 코드 몇 번째
줄에서 왔는지"는 표준적으로 안 남습니다. 그래서 이 신경망이 실제 하드웨어에서 이상하게
동작할 때, "그게 원래 파이썬 코드의 어느 부분 때문이었는지" 추적할 방법이 없습니다.

**우리 목표**: 이 파이프라인에 MLIR/DWARF 방식을 참고해서, 실제로 디버깅(중단점, 변수
추적)이 가능하도록 소스 위치 정보를 끝까지 보존하는 설계를 만드는 것.

---

## 2. 실제 프로덕션 파이프라인 (부산대가 만든 것)

```
ONNX 모델
  → (admit 단계 - 우리가 만짐)
  → onnx → harx → EmitC   ← 부산대(PNU)가 만든 mlir-arx 컴파일러 (우리가 절대 안 건드림)
  → (tail 단계 - EmitC → C, requant repair, link - 우리가 소유)
  → 실제 ARX 하드웨어 위에서 실행
```

- **admit 단계**: "ONNX를 파이프라인에 들여보내는 입구"라는 뜻. ONNX 파일을 막 읽어들인
  직후 시점을 말합니다. 여기서 **우리가 직접 손댈 수 있습니다.**
- **중간(onnx→harx→EmitC)**: 부산대의 `mlir-arx`라는 실제 컴파일러가 하는 일. **우리는
  이 안을 절대 수정하지 않습니다** — 라이선스 이슈도 있고, 애초에 우리 역할이 아닙니다.
- **tail 단계**: "파이프라인의 꼬리(끝부분)"라는 뜻. EmitC(컴파일러가 만든 C 비슷한
  중간 표현)가 진짜 C 코드로 바뀐 다음부터를 말합니다. 여기도 **우리가 손댈 수 있습니다.**

즉 **우리가 만질 수 있는 곳은 맨 앞(admit)과 맨 뒤(tail) 두 군데뿐**이고, 중간(mlir-arx
내부)은 블랙박스로 취급합니다.

---

## 3. 이 도커 환경의 정체

지금 작업 중인 이 컨테이너는 **부산대의 진짜 ARX 컴파일러가 원래 들어있는 환경이
아닙니다.** 업스트림(공개) `onnx-mlir` 0.5.1을 기반으로 한 일반적인 개발 환경입니다.
그래서 원래는:

> "같은 MLIR 인프라 위에서 provenance(위치 정보)가 얼마나 보존되는가"를 검증하는
> **실험대**로 사용

...하는 용도였습니다. 즉 실제 부산대 컴파일러 없이, "일반적인 MLIR 컴파일러라면 이런
정보들이 어디까지 살아남을까"를 먼저 검증해온 겁니다.

**최근에 상황이 바뀌었습니다** — 부산대가 실제 저장소(GitHub/GitLab) 접근 권한을 줘서,
이 실험대가 아니라 **진짜 부산대 컴파일러를 직접 빌드해서 실측 검증**할 수 있게 됐습니다
(4번 항목에서 설명).

## 4. 우리가 만든 실험 도구 (admit + tail)

`debug_info_investigation/` 폴더 안에 있는 3개의 파이썬 모듈이 핵심입니다.

### 4-1. `info_track.py` — admit 단계 (정보를 "뽑아내는" 쪽)

- PyTorch에서 `torch.onnx.export(model, ..., dynamo=True)`로 ONNX를 만들면, PyTorch가
  **자동으로** 각 연산(노드)에 "이 연산이 원래 어느 파이썬 파일 몇 번째 줄에서 왔는지"라는
  정보를 `metadata_props`(ONNX 파일 안의 부가정보 필드)에 심어줍니다. 이건 우리가 만든 게
  아니라 **PyTorch 자체의 기능**입니다(`torch/onnx/_internal/exporter/_core.py`의
  `_set_node_metadata()` 함수가 하는 일 — 실제 소스에서 확인함).
- `info_track.py`는 이걸 읽어서 `{node.name: {file, line, source, module_scope, ...}}`
  형태의 JSON(**locmap**이라고 부름)을 만듭니다.
- 왜 필요한가: onnx-mlir(뒤에서 이 ONNX를 실제로 처리하는 컴파일러)은 이 정보를 그냥
  버립니다. 그러니까 컴파일러에 넘기기 **전에** 우리가 따로 떠놔야 합니다.

### 4-2. `code_track.py` — tail 단계의 대역(stand-in)

- 실제 프로덕션에서는 `EmitC → C` 변환을 부산대의 mlir-arx가 해줍니다. 근데 이 도커엔
  진짜 mlir-arx가 없었어서(최근까진), **가짜 C 코드 생성기**로 대체해뒀습니다.
- ONNX 그래프에서 `node.name`과 `op_type`만 읽어서, 노드마다 "가짜 연산"(실제 계산은 안
  하고 `buf[i] = buf[i]*1+0` 같은 의미 없는 코드)이 들어있는 C 함수를 만듭니다. 각 함수
  안에 `/* onnx_node_name: <이름> */`라는 **주석 마커**를 남겨둡니다.
- 진짜 EmitC가 생기면 이 함수의 **내용물만 교체**하면 되도록 설계해뒀습니다(함수
  시그니처는 "ONNX 경로 받아서 C 문자열 돌려주기"로 고정).

### 4-3. `join.py` — 두 트랙이 만나는 유일한 지점

- `info_track.py`가 만든 locmap과 `code_track.py`가 만든 C 코드를, **`node.name`이라는
  이름 하나로 매칭**시킵니다.
- 매칭되면, C 코드의 그 자리에 `#line <원본줄> "<원본.py>"`라는 **C 전처리기 지시자**를
  삽입합니다. 이건 컴파일러(gcc)한테 "지금부터 나오는 코드는 사실 이 파이썬 파일 이
  줄에서 온 거야"라고 알려주는 겁니다.
- 이렇게 `#line`이 심긴 C를 `gcc -g`로 컴파일하면, 실제로는 C 코드인데 **DWARF에는 원본
  파이썬 파일:줄이 그대로 찍힙니다.** 그래서 `gdb`로 파이썬 소스 줄에 중단점을 걸 수
  있습니다 — 실측으로 이미 검증 완료 (`readelf`/`gdb`로 직접 확인).

### 4-4. 왜 이런 우회를 하나

정식 방법(MLIR → LLVM dialect → 진짜 DWARF)도 시도해봤는데 실패했습니다(`--enable-debug-
info` 옵션 — onnx-mlir이 자동 생성하는 런타임 헬퍼 함수들의 위치정보가 없어서 컴파일러
자체 검증 단계에서 에러남). 그래서 "생성된 C에 `#line`을 심어서 표준 `gcc -g`/DWARF에
얹혀가는" 우회 방법을 택했습니다.

## 5. 이번에 진짜 부산대 자료를 받고 확인한 것

부산대가 GitHub/GitLab 접근 권한을 줘서, 실제 컴파일러를 **직접 클론해서 빌드**했습니다
(LLVM 커밋까지 정확히 맞춰서, 우리 프로젝트와 충돌 안 하게 완전히 격리된 경로에).

### 받은 것 두 가지

1. **`mlir-arx`** (github.com/SOTA-PNU/mlir-arx) — 실제 컴파일러. 업스트림 onnx-mlir을
   확장해서 **ARX**(Advanced RISC eXtended, INT8 양자화 전용 AI 하드웨어 가속기)를
   지원합니다. `HARX`라는 MLIR dialect(ARX 하드웨어가 실행할 연산들을 표현하는 소프트웨어
   중간 표현 — 하드웨어 자체가 아님, 컴파일러 내부 표기법)를 새로 추가했습니다.
2. **`arx-api`** (github.com/SOTA-PNU/arx-api) — 처음엔 "컴파일러가 쓰는 하드웨어 API"라고
   생각했는데, **실제로 확인해보니 mlir-arx 컴파일러 빌드에는 전혀 안 쓰입니다.** 서브모듈로
   받아지긴 하는데 어떤 CMakeLists.txt도 참조를 안 합니다. 폴더 구조로 볼 때 이건 **컴파일
   타임이 아니라, 컴파일된 코드가 실제 ARX 칩 위에서 돌아갈 때 쓰는 런타임 라이브러리**로
   보입니다 — 그래서 우리 작업(컴파일 타임 provenance 보존) 범위 밖입니다.

### 실제로 확인한 4가지 핵심 발견

실제 mlir-arx 컴파일러를 빌드해서, `--mlir-print-debuginfo`(위치정보를 텍스트로 찍어서
보여주는 옵션)를 켜고 직접 실행해봤습니다.

1. **ONNX 노드 이름(`onnx_node_name`) 자체는 중간 하드웨어 전용 표현(HARX)으로 바뀌면서
   속성으로는 사라집니다.** 하지만 원본 모델 코드(`RewriteOnnx.cpp`)를 읽어보니, 새 연산을
   만들 때마다 예외 없이 원본 위치정보(`loc()`)를 그대로 넘겨주고 있었고, 실측으로도
   확인됐습니다 — 대신 `harx_name`이라는 새 이름표(예: `"convolutionshift_9"`)가 붙습니다.
2. **그다음 단계(EmitC, 진짜 C++ 만들기 직전 표현)까지도 위치정보가 살아있습니다.**
   `harx_name`이 최종 변수 이름에 그대로 박히고, 위치정보(`loc()`)도 별도로 남아있는 걸
   실제 파일로 확인했습니다.
3. **근데 그다음, `mlir-translate`(부산대 코드가 아니라 LLVM/MLIR 표준 도구)가 진짜 C++로
   바꾸는 바로 그 순간 위치정보가 완전히 사라집니다.** 이건 실제로 위치정보를 붙인 가짜
   MLIR을 만들어서 이 도구에 직접 넣어보고 확인한 겁니다 — 옵션을 바꿔봐도 안 살아남습니다.
   다만 **변수 이름(harx_name에서 온)은 그대로 살아남습니다.**
4. **ARX는 양자화(INT8)된 모델만 받습니다** — 일반 float 모델을 넣으면 컴파일 에러가
   납니다. PyTorch에서 최신 양자화 방식(PT2E)으로 양자화해봤더니, 양자화된 연산들에도
   `stack_trace`(원본 위치정보) 정보가 100% 살아있는 것도 확인했습니다.

### 결론: 전체 사슬이 완성됐습니다

```
.py 파일:줄
   ↕ (PyTorch가 자동으로 기록)
ONNX 노드 이름
   ↕ (실측 확인: mlir-arx가 위치정보를 그대로 넘김)
HARX 연산 (harx_name 이름표 + 위치정보 둘 다 붙음)
   ↕ (실측 확인: harx_name이 변수 이름에 그대로 박힘)
EmitC 변수 이름
   ↕ (기존에 확인: mlir-translate가 이름은 보존, 위치정보만 버림)
최종 C++ 변수 이름
```

**"변수 이름"이라는 단 하나의 끈이 처음부터 끝까지 안 끊깁니다.** 그러니까 우리가 만든
`join.py`가 지금은 "ONNX 노드 이름" 마커로 하는 일을, "EmitC/최종 C++ 변수 이름"을
키로 바꾸면 실제 부산대 파이프라인에도 그대로 적용할 수 있습니다.

**아직 부산대 컴파일러 소스는 단 한 줄도 안 고쳤습니다** — 전부 읽기+실행만 했습니다.
이건 매우 중요한 원칙입니다 (2번 항목 참고, 절대 안 건드리는 영역).

## 8. 다음에 할 일 (아직 안 끝남)

1. **`join.py`의 조인 키를 "ONNX node.name"에서 "harx_name/변수이름"으로 바꾸기** — 지금은
   설계만 확정됐고 코드는 안 짬.
2. **우리 양자화 모델이 부산대 컴파일러를 실제로 통과하게 만들기** — 부산대가 실제로 쓰는
   양자화 도구/스킴이 뭔지 확인 필요.
3. **끝까지 이어서 gcc -g/gdb로 실측 검증** — EmitC까지만 확인했지, "실제로 gdb에서 파이썬
   줄에 중단점이 걸리는지"는 진짜 파이프라인 기준으로는 아직 안 함.
4. 부산대/경북대에 보낼 "Debugger 연계 협의" 자료 업데이트 (입력 대상/관측 지점/출력 형식).
